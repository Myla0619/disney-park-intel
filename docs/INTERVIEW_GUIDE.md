# 乐园长程规划 Agent｜面试口述稿

## 1. 请用三分钟介绍这个项目

我做的是迪士尼一日游规划 Agent，是在老师的长程出行规划方案上做乐园场景改造。它解决的是游客同时有多项要求时，怎么把需求变成一份可以执行的时间表。比如带孩子下午入园，希望少走路、避开不适合孩子的项目，还要保留烟花和离园时间。这里需要把项目限制、排队、区域间步行和演出安排放在一起考虑。

系统里，模型负责理解需求和选择工具，规划工具负责计算路线，校验器负责检查交付结果。一次典型交互是：先查项目身高要求和排队，再根据需要补充评论、步行或演出信息，把游客偏好传给行程规划工具，最后输出带项目和起止时间的结构化行程。现在注册了九个工具，训练、蒸馏和评测都使用同一套工具名称、参数校验和返回格式。

训练路线是 Qwen2.5-32B-Instruct 的全参 SFT 加全参 GRPO。SFT 学习教师在这些工具上的完整执行示范；GRPO 让学生对同一个任务生成多条交互轨迹，根据实际执行结果学习工具取舍和错误恢复。工具观察会回到上下文，但不作为模型生成的动作计算训练损失。

数据上，我已经构建了 306 个乐园任务家族，包含排队查询、评论判断、亲子规划、多意图和路线权衡等类别。先固定训练、验证和测试家族，再让教师扩写表达。扩写必须保留时间、身高、项目名称和否定条件，之后才让教师调用工具生成轨迹。轨迹还要经过协议检查、工具执行检查、最终行程校验和质量评审。

我在乐园场景里重点补的是最终行程的证据检查。例如规划工具给了正确时间表，模型却在最终答案里改了时间，不能仍然拿到高奖励。现在最终行程要和最后一次成功规划的结果对应，再按原始游客偏好检查身高、入离园时间和演出是否满足。检查失败时，规划总奖励归零。

目前已经完成种子构建、工具环境以及训练评测链路的本地验证。教师批量生成和全参 GPU 训练还没有完成，因此当前交付是可以继续开展训练的工程链路，尚无这版模型的效果提升数据。我的主要工作是把老师的方案落到乐园工具、任务数据、行程校验和多轮训练接口上。

## 2. 为什么选择训练 Agent，而不是强模型配合 Prompt？

我训练这个 Agent，是为了让模型稳定完成“查询乐园信息、调用规划工具、交付合规时间表”这一整条流程。这里不仅需要理解游客的话，还需要反复遵守同一套工具协议，并把前面查到的结果用于后面的安排。

SFT 首先解决执行一致性。例如游客说孩子身高有限、下午入园，模型需要把这些条件传进规划参数，不能只在答案里说“适合亲子”。我把工具请求、真实返回和最终答案放进同一条示范，让模型学习从游客需求到参数、再到行程的对应关系。

GRPO 进一步优化多轮取舍。例如同一个任务里，一条轨迹反复查排队，另一条轨迹查完排队和步行后直接生成可行路线，我希望训练反馈鼓励后者。对于改错离园时间、遗漏指定烟花的答案，即使文字流畅，也会被最终行程检查拦住。

选择开源模型训练，还让我能够自行部署和管理乐园版本。以后增加工具或发现某一类亲子规划失败，可以更新相应轨迹和奖励规则，再迭代模型。所以这条路线的价值是把乐园执行流程学进模型，并围绕实际任务结果持续优化。

## 3. 306 条种子怎么获得？怎样扩展成训练数据？

这 306 条是用乐园任务模板构建的原始任务家族。模板按排队查询、评论判断、项目详情、规划、多意图、否定条件和权衡等十二类组织，并保存园区、问题、结构化游客偏好和任务类别。比如“某项目排多久”和“带孩子、少走路、还要看烟花”对应不同的任务类型和约束组合。

我先给原始任务固定家族标识和数据划分，再进行表达扩写。这样“孩子身高 110 厘米”和“带一个 110 厘米的孩子”如果来自同一道种子，只能留在同一个集合，不会一条用于训练、另一条用于测试。

扩写脚本要求教师为每条种子生成五种说法，并保留原句。先检查数字等约束是否保留，再调用教师做语义等价复核，最后做文本去重。原句说“不玩刺激项目”，改写就不能变成“喜欢刺激项目”。合格查询再进入蒸馏，让教师真实调用工具，记录完整执行过程，随后清洗成 SFT 样本。

当前完成的是 306 条种子。扩写配置的目标是至少一千八百条候选查询；它们还需要经过实际执行和清洗，才能计入合格训练轨迹。

## 4. 一条轨迹具体长什么样？

我用一条亲子规划任务举例。记录开头保存任务编号、家族编号、数据集合、园区、用户问题、孩子身高等偏好、教师模型和环境快照。后面保存完整消息序列，以及最终答案、工具调用次数、格式错误和停止原因。

模型输出用三个标签表示：think 是简短决策说明，tool_call 里是工具名和参数 JSON，answer 是最终交付。例如模型先输出调用 get_spot_info 的请求，执行器查询项目后，把带 ok 状态和结果的 tool_response 写回下一条观察消息，模型再决定是否调用 plan_itinerary。

规划答案要求有 summary 和 itinerary。行程项包含项目 ID、名称、类型、开始和结束时间，评分器可以直接解析。SFT 监督历史中的 assistant 输出；GRPO 保留模型生成 token 的概率，工具返回的 token 掩码设为零，避免把环境给出的排队数字当作模型动作来训练。

## 5. DeepSeek-V3 在这个项目里做什么？怎样控制质量和多样性？

我的方案把 DeepSeek-V3 用作教师，承担两个具体任务：改写乐园问题，以及在学生同样要使用的工具环境里生成示范。教师不是直接写一篇游园攻略，而是先输出工具请求，拿到执行器的结果，再继续生成下一步，直到交付答案。

多样性由任务模板和表达风格共同控制。模板覆盖亲子、少走路、指定演出和多意图等情况；表达扩写分别使用口语、简短提问、分点需求、先说目标和先说顾虑。改写生成温度设为 0.8，语义复核设为 0，让生成和审核承担不同职责。

质量控制分两段。扩写阶段检查项目、数字、否定和条件有没有被改掉；蒸馏阶段检查实际调用、协议和最终答案。每次生成记录教师模型、端点和输入摘要，断点续跑时配置不一致就拒绝复用旧结果，避免把不同实验的轨迹混在一起。

## 6. 多阶段质量过滤具体淘汰什么？

第一步淘汰没有完成任务的轨迹，包括教师接口报错、超时、没有答案、严重格式错误，以及需要查询却没有调用工具的样本。常识类任务单独处理，允许直接回答。如果模型自己在 assistant 消息里伪造 tool_response，也直接拒绝。

第二步检查工具和协议。全部工具都失败的轨迹不进入训练；部分失败但后续取得结果的轨迹可以继续审核。清洗器去掉 assistant 标签外的闲聊文字，再用同一个协议解析器检查，避免训练时学到一套格式、执行时要求另一套格式。

第三步检查规划结果。例如亲子行程必须带原始游客偏好，最终 JSON 行程必须和真实规划输出一致，再检查身高、时间和演出。把项目换成不存在的 ID，或者只写“我已经安排好了”而没有结构化行程，都会被拒绝。

最后才调用 Judge 做语义质量筛选，检查是否回答了游客的问题、需求是否完整、结论是否有工具证据。低质量样本剔除，合格但有瑕疵的样本标为边界质量。每条拒绝原因和最终保留数量都会写入清单，后续可以按原因检查数据问题。

## 7. 为什么按调用次数分级？实际怎么分？

我们按工具调用次数分级，主要是为了实现由短到长、由简单到复杂的课程学习。

在乐园任务里，查询一个项目的排队时间，可能一次调用就能完成；但安排亲子行程，需要结合项目身高限制、排队、步行和演出信息，连续调用多个工具。交互链越长，模型越需要记住游客约束，并根据前面的结果决定下一步。

具体实现中，清洗器把不超过三次调用的轨迹标为 easy，四到十次标为 medium，超过十次标为 hard。训练前期先使用 easy 和 medium，让模型学会工具协议、参数填写和读取返回结果；后期再加入 hard，学习多工具配合和完整行程规划。

这样安排的好处是，把基础执行能力和长程决策分阶段学习，减少模型在还没掌握工具调用时，就同时处理大量约束和复杂交互的负担。例如先学会正确查询项目和排队，再学习怎样把这些信息用于一份不超过离园时间的路线。

调用次数是我们划分交互长度的实用指标。同时，奖励里会对重复调用扣分，避免模型通过多查几次，把无效操作当成复杂推理。

## 8. 边界样本动态降权具体怎么实现？

在我的清洗器里，没有格式错误、没有答案修复、没有失败调用的合格轨迹标为 pass；有格式修复或部分调用失败的合格轨迹标为 borderline。Judge 也可以把语义质量处于边界区间的样本降到 borderline。最终行程不合格的样本会被删除，不进入降权训练。

全参 SFT 使用 LLaMA-Factory，我没有只往数据里写一个 weight 就结束，而是在预处理阶段把权重转换成实际曝光次数。前、中、后期，边界样本相对高质量样本的曝光比例分别是 0.30、0.45 和 0.60。

比如早期一个高质量样本出现十次，对应的边界样本出现三次。这样模型先多看规范的乐园工具流程，后面再提高包含修正过程的轨迹占比。各阶段输出清单记录重复次数和原始任务编号，验证集不随曝光策略变化。

## 9. SFT 后为什么还需要 GRPO？

SFT 给我的模型一个规范起点：游客提出需求后，怎样查项目、怎样调用规划、怎样输出行程。但教师示范主要告诉它一条已经走出来的路径，学生自己执行时可能先查错工具、重复查询，或者忘记把游客的离园时间传进规划。

GRPO 在这里让学生自己走完整个交互过程。同一个游客任务采样八条轨迹，有的可能正确完成，有的可能工具失败后恢复，有的最终行程不合规，再用这些结果比较同题下的行为好坏。

我给重复调用扣效率分，对没有恢复的失败施加更大惩罚，并对不合规的最终规划归零。这样 SFT 学到的工具流程可以继续围绕“少走无效步骤、正确恢复、交付可行行程”优化。

## 10. 这个项目的 GRPO 目标函数是什么？和 PPO 有什么区别？

我的配置对同一个乐园任务采样八条完整轨迹。每条轨迹先经过六维奖励和最终行程检查，再用“该轨迹奖励减去组内平均奖励，除以组内标准差”的方式得到相对优势，实际计算还会做数值稳定处理。

策略部分使用新策略相对采样策略的 token 概率比，分别计算原始项和裁剪项，再取较小值；同时减去相对固定 SFT 参考模型的 KL 惩罚。这里参与更新的是模型的决策、工具请求和答案 token，工具返回的观察不参与动作损失。

实现使用 veRL，优势估计配置为 grpo。和使用价值网络的 PPO 路线相比，这里用同题组内奖励代替价值模型估计，不额外训练 critic；代价是每题要生成多条交互轨迹。

这个项目需要特别关注整组行程都不合格的情况：如果八条轨迹都被硬校验归零，组内就没有有效差异。我会从保存的 rollout 检查是模型没有学会协议，还是任务约束不可满足，再处理对应的数据或任务。

## 11. 六维奖励在代码里分别怎样算？

第一维是格式分。从一分开始，减去格式错误数占交互步数的比例，答案经过格式补救或没有答案还会额外扣分，最后限制在零到一。

第二维是轨迹合理性，按任务类别检查工具。例如排队题检查 get_wait_times，评论题检查 search_reviews，规划题检查 plan_itinerary。多意图和权衡题检查是否使用了至少两种工具；常识题则鼓励不调用工具直接回答。

第三维是效率分。代码把工具名和参数序列化成请求签名，统计完全相同的重复调用，再检查是否超过该类难度的调用预算。每次重复扣 0.2，每次超出预算扣 0.1，分数最低为零。

第四维是行程约束。先解析最终答案里的 itinerary，和最后一次成功规划输出核对项目、类型和时间，再按原始游客偏好检查项目是否存在、身高是否合规、时间是否冲突、入离园窗口和指定演出。

第五维是调用状态。失败后同名工具在后续成功，按一次恢复失败扣 0.1；没有后续成功则扣 0.25。因此模型修正参数后完成调用，比一直失败得到的反馈更好。

第六维是答案质量。Judge 对相关性、完整性、事实依据、工具使用和清晰度分别打分，合计除以总量程，转换成零到一。最后加权组合；如果规划结果不合规或无法验证，总分直接归零。

## 12. 六种奖励怎么组合？怎样控制过程奖励刷分？

这个项目的答案质量权重在前、中、后期分别是 0.60、0.68 和 0.75。随着训练推进，格式和调用状态等过程分的相对权重下降，约束分权重保持不变，各阶段权重之和都是一。

乐园任务最需要防的是“流程看起来正确，时间表却不能执行”。所以我在加权以外增加最终行程门控：即使格式分和 Judge 分都很高，只要最终答案改错时间、缺失指定演出，或者与真实规划输出不一致，总奖励仍然为零。

每条轨迹同时保存六个分项、加权总分和门控原因。这样出现总分变化时，可以直接定位是答案改善、重复调用减少，还是课程权重变化，而不是只看一条总奖励曲线。

## 13. 简历里的组合奖励提升，应该怎样回答？

我目前没有这版全参模型从 0.29 提升到 0.96 的同口径实验记录，因此没有把这组数字作为本项目结果。当前奖励已经加入最终行程门控，也有分阶段权重，需要用新版评测重新产生数据。

具体评测时，我把基座、SFT 和 GRPO 模型放到相同的测试任务、系统提示词和乐园快照上，固定评分阶段，保留每一道题的完整轨迹和奖励分解。比如比较同一道亲子规划题时，两边看到的排队和演出信息必须一样。

我会同时看最终行程是否通过约束、是否产生有效答案，以及逻辑工具调用的成功情况。这样可以把“奖励定义下得分更高”和“游客实际拿到更可行的行程”对应起来。

## 14. 举一个这个项目真实验证过的失败案例。

我在回归测试里构造了一条上海迪士尼亲子任务，孩子五岁、身高 110 厘米。脚本化模型真实调用沙箱里的规划工具，再把返回的行程完整写进答案，这条轨迹可以通过清洗和最终行程校验。

然后我只把最终答案里第一项的开始时间改成凌晨零点，中间工具返回保持不变。旧的评分思路如果只信中间的 constraintsPassed，就可能漏掉这次改写。现在评分器会比较最终行程和最后一次成功规划的签名，这条轨迹被拒绝；即使测试 Judge 给满分，也不能绕过门控。

同一组测试还覆盖了虚构项目 ID、缺少要求的烟花，以及只写一段“行程没问题”而不交付结构化时间表。这些都是本地验证过的奖励和执行反例，不是 GPU 训练日志里观察到的模型行为。

## 15. KL 在这个项目里怎么设置？能解决什么问题？

我的 GRPO 配置在 actor 损失里启用 KL，初始系数设为 0.001，参考模型固定为最后阶段的 SFT 完整权重。进入后续课程阶段时，训练策略继续恢复，KL 参考仍然保留原来的 SFT 模型。

这样做是为了在优化乐园任务奖励时，保留 SFT 学到的工具协议和基本回答能力，降低策略为追求某个奖励项突然偏移的幅度。例如效率分鼓励少调用，但模型不能因此退化成不查排队、直接编路线。

最终行程被改写这类漏洞由证据校验器处理，KL 负责限制更新幅度。系数过大时，学生难以改善 SFT 阶段的重复查询；过小时，则需要关注协议错误和无依据作答有没有增加。我的检查对象是 KL、完整轨迹和奖励分项一起变化的情况。

## 16. 课程式训练实际怎样切换？

SFT 有 early、mid、late 三份配置。early 只使用 easy 和 medium 轨迹，后面加入 hard，并提高边界样本的相对曝光。三个阶段使用同一份验证数据，后一阶段加载前一阶段的完整权重；当前每阶段设置了一百个更新步作为初始运行预算。

GRPO 也按阶段准备数据，并切换对应的六维奖励权重。启动 mid 或 late 时必须提供上一阶段 checkpoint，继续恢复策略和优化器，而 KL 参考仍然是固定 SFT 模型。

当前代码是显式指定阶段启动，不是根据指标自动切换。实际运行时，我会检查保存的验证轨迹是否仍能正确调用工具、交付合规行程，再判断是否继续下一阶段。阶段配置和恢复路径都会保存在输出目录，能够追溯一次训练到底用了哪份数据和权重。

## 17. Agent 如何在工具之间选择？

我这个版本是九个注册工具：排队 get_wait_times、评论 search_reviews、规划 plan_itinerary、详情 get_spot_info、演出 get_show_schedule、优速通 get_ll_pricing、步行 walk_time、校验 check_constraints 和天气 get_weather。

工具名称、描述和参数 schema 来自统一注册表，并自动写进系统提示词。模型输出工具名和 arguments，执行器检查必填字段、类型和枚举之后才执行。例如查项目详情必须给园区、地点 ID 和地点类型；步行工具需要起点和终点区域。

选择工具时，亲子适配先看详情里的身高和刺激程度，体验问题再查评论；排队权衡看排队数据，完整路线交给规划工具。规划工具内部会结合项目评分、排队和演出锚点生成时间表，因此 Agent 不需要手工编造每一个时间点。

## 18. 详情和步行等工具有重叠时怎么选？

项目详情工具在提供 current_area 时，会顺带返回到该项目所在区域的步行时间。如果游客问“这个项目适不适合孩子，从这里过去要多久”，一次详情查询就可以同时提供身高要求、刺激程度和步行信息。

如果问题只涉及两个区域之间的距离，直接用 walk_time，它的参数和输出更集中。评论检索则用于补充怕黑、体验感等文本证据，不用它代替详情表里的身高限制。

规划工具内部已经读取排队数据并计算路线，所以如果任务只要求生成完整行程，可以直接进入规划；只有用户还要求解释排队权衡或比较具体项目时，再补充查询。这些选择通过示范轨迹传给模型，完全重复的请求还会被效率奖励扣分。

## 19. 参数错误、超时、空结果和冲突怎么处理？

参数错误在执行前返回 ok 为 false 的错误结果。例如 walk_time 的区域 ID 不属于当前乐园，工具会返回“未知区域”，模型下一轮可以修正参数。未知工具名也会返回可用工具列表，不会执行一个猜测的替代工具。

教师接口的暂时性错误由调用器有限重试，工具 HTTP 请求有超时，整个蒸馏任务也有总时限。超时或没有最终答案的轨迹会被记录为失败并由清洗器剔除；模型能收到的工具错误，则作为下一轮观察保留。

评论检索返回空结果时，Agent 需要换检索词或明确缺少评论证据，不能把空结果解释成项目不存在。演出数据没有快照时，工具会返回默认时间并标记 source 为 default；这个默认信息不能包装成刚查询到的官方实时场次。

当前训练用固定快照控制数据变化，没有做跨供应商的自动冲突裁决。对最终行程，系统采用明确的依据规则：必须对应最后一次成功规划结果，模型不能把几次不一致的返回随意拼成一张时间表。

## 20. 工具调用成功率怎么统计？

我在评测里按模型发出的逻辑请求统计。比如模型先用错误区域调用 walk_time，收到错误后修正区域再调用成功，这里分母是两次，分子是一次。接口内部为了完成同一个请求进行的网络重试，不再增加逻辑请求数。

成功看业务返回的 ok，不只看 HTTP 状态码。工具执行器可能用 HTTP 200 返回一个参数错误信封，这种请求仍然算失败。

任务完成另看最终交付：排队查询拿到数据以后是否回答问题，规划任务是否输出有效结构化行程并通过检查。当前没有这版独立评测支持的“99% 以上”结果，所以我保留分子、分母和逐条调用记录，等实际评测后再报告比例。

## 21. Key 轮询具体怎样保证并发安全？

教师调用器使用共享 KeyPool，每个 Key 记录正在执行的请求数、冷却截止时间和是否停用。分配时先同步增加占用，再发请求；结束时通过租约释放，并防止重复释放，默认每个 Key 同时最多两个请求。

扩写脚本有多个 worker，同一进程里使用相同 Key 列表时会拿到同一个池。这样两个 worker 不会都看到“这个 Key 还有空位”，随后一起超额分配。

遇到 429 时，调用器解析 Retry-After，再把 Key 放进冷却；401 或 403 会停用对应 Key；服务端暂时性错误也会触发冷却。等待 Key 和请求重试共用总时限，避免一条教师任务一直挂起。当前这套占用计数的范围是单进程，多台机器共享配额需要另设统一协调。

## 22. 上下文具体保留了什么？有没有做压缩？

当前乐园执行循环保留系统工具说明、用户问题、历史 assistant 输出和真实工具反馈。它没有实现自动摘要替换历史消息，所以我不会把它叫作语义压缩或长期记忆。

实现的是预算控制：蒸馏循环默认按六万字符检查上下文，工具反馈加入后接近八成预算，就提示模型停止查询、根据已有证据交付答案；超过上限则结束并记录 context_budget。达到调用预算也会触发收尾提示。

GRPO 侧使用 token 预算，过长的初始提示会报错，生成被截断时不能拿完整轨迹的奖励去训练截断后的内容。这个处理重点是避免孩子身高、离园时间等条件被静默截掉，也避免训练内容和评分内容不一致；目前没有“压缩后信息完全保留”的实验结论。

## 23. 怎样阻止前面的错误传到最终行程？

我设置了三个检查位置。调用前检查工具参数，调用后把 ok 和具体错误返回模型，交付时再检查最终结构化行程。

例如模型传错项目 ID，详情工具会立即返回不存在，而不是继续编造项目信息。模型之后可以修正 ID，再查询和规划。规划工具本身会返回约束检查状态，但奖励器还要使用任务原始偏好重新检查最终答案，不能让模型通过传宽松的身高或离园条件降低要求。

如果模型重新规划，最后答案必须对应最后一次成功的规划结果。部分失败后完成任务的合格轨迹会保留为边界样本，调用状态奖励也对恢复后的失败少扣分，把“看到错误后修正”纳入训练反馈。

## 24. 排队或天气变化后，怎么重新规划？

现有工具接口支持重新发起规划。比如用户反馈某个室外项目暂停，Agent 可以把它加入 avoid_rides，用 start_area 指定当前区域，并更新剩余时间窗口后调用 plan_itinerary，再交付新的结构化时间表。

这里不能只改旧答案中的项目名称，因为换项目会影响步行、排队和后续演出。最终证据检查也要求答案对应新的成功规划结果，直接改旧时间表会被拒绝。

当前天气工具使用固定日期生成沙箱天气，用于复现天气相关任务；还没有接入可用的实时天气服务，也没有后台自动监控游客已完成项目的状态。因此当前实现覆盖的是收到变化信息后的再次工具调用，不是自动跟踪游客并主动推送重规划。

## 25. Judge 具体看哪些内容？怎样减少偏差？

单轨迹 Judge 看游客任务和执行消息，从五个维度各打零到十分，再合计归一化。相关性看是否回答了这道乐园问题；完整性看亲子、离园和演出等需求是否遗漏；事实依据看排队、限制等结论能否在工具返回中找到；工具使用看查询是否支持决策；清晰度看游客能否读懂安排。

Judge 必须返回规定的维度和理由。维度缺失、越界或解析失败会报错，不会默默补一个中间分。最终行程的硬约束仍由程序检查，Judge 给出的好评不能覆盖约束失败。

模型对比使用另一个交叉评测入口：隐藏模型身份，把同题两条轨迹作为 A 和 B，再交换位置重复评审。提示词明确要求按需求、可行性和证据判断，不因篇幅和排版加分；配置还会排除学生和教师模型身份，减少自己评价自己生成风格的情况。

## 26. 多个 Judge 冲突时，系统怎么处理？

交叉评测要求至少两个不同的 Judge，并先核对两份模型结果的任务、协议摘要和环境快照一致。每个 Judge 对同一道题评两次，第二次交换 A、B；保存结果时把票数映射回原模型，避免交换位置以后把胜负记反。

如果同一个 Judge 交换位置后结论变了，或者不同 Judge 分别支持两边，记录就会标记 reviewRequired。输出保留模型身份、每次判断和证据理由，不只保留平均偏好。

复核时我会先看这道乐园题的客观信息。例如一边表述更漂亮，但遗漏了用户指定烟花，先用演出约束确定问题，再看 Judge 为什么忽略了它。系统目前把分歧留给复核，不会自动请另一个模型投票后覆盖原始分歧。

## 27. 迁移成企业经营分析 Agent，哪些模块可以复用？

我会保留现在的多轮执行循环、工具注册表、参数校验、错误信封和轨迹记录，把乐园工具替换成经营分析工具。比如把排队查询换成销售数据库查询，把行程计算换成利润和同比计算，把评论检索换成经营文档检索。

乐园版把模型生成内容和真实工具观察分开，这一点可以直接复用到经营分析：数据库返回的销售额是观察，模型选择查询范围和解释变化是动作，训练时仍然只更新模型生成的部分。

最终行程证据检查也可以迁移。乐园里我检查答案的项目和时间是否对应规划输出；经营分析里则检查报告中的收入、成本和同比是否对应查询与计算结果，并固定时间范围、币种和指标口径。

需要重新建设的是企业权限和业务规则。数据库工具必须在执行前校验访问范围，不能只靠提示词要求模型保密；奖励里的身高、演出和离园约束，也要替换成指标口径、数值一致性和来源可追溯检查。

# 关键数字与技术选择：六段式追问答案

## A. 306 条任务种子

**定义：**“306 是已经生成的乐园原始任务家族数，每条有问题、园区、游客偏好和类别，不是蒸馏轨迹数。”

**基线：**“数据对照使用这些原始问题；加入教师改写后，比较模型对同类需求不同说法的处理。”

**实验设置：**“原始家族固定为 246 个训练、30 个验证和 30 个测试，所有改写继承家族归属。这个划分已经写入种子文件和清单。”

**提升原因：**“扩写让‘下午带娃入园’和分点列出的亲子需求都能进入示范，同时保持孩子身高和离园条件不变。”

**失败案例：**“把同一亲子题的原句放训练、口语改写放测试，会把记住同一道题当成泛化；家族划分就是针对这个问题。”

**个人贡献：**“我把老师的长程任务结构改成乐园类别和游客偏好，并在扩写前固定家族归属。”

## B. 教师扩写和轨迹蒸馏

**定义：**“每条种子生成五种表达并保留原句，去重后的查询目标至少一千八百条；查询还要经过教师实际执行和清洗，才能成为训练轨迹。”

**基线：**“原始模板查询是表达覆盖对照，清洗前的教师轨迹是数据质量对照；当前批量生成还没有完成。”

**实验设置：**“改写逐条做数字检查和语义复核；蒸馏固定乐园快照，让教师通过同一执行器拿到工具返回，记录完整消息和停止原因。”

**提升原因：**“表达变化覆盖游客问法，工具执行让学生看到查询和返回的对应关系，清洗阻止错误时间表进入示范。”

**失败案例：**“把‘不玩刺激项目’改成‘想玩刺激项目’必须拒绝；教师生成途中超时、没有最终答案，也不能按完成轨迹计数。”

**个人贡献：**“我把约束保持检查、生成日志、断点恢复和合格数量清单接进数据流程，避免只扩写文本却没有执行轨迹。”

## C. 全参数 SFT

**定义：**“项目主线使用 Qwen2.5-32B-Instruct 完整模型，LLaMA-Factory 配置为 full；GRPO 同样不启用 LoRA adapter。”

**基线：**“模型效果对照是同一个 Qwen 基座、SFT checkpoint 和 GRPO checkpoint，用相同乐园题和环境回放评测。”

**实验设置：**“SFT 使用 BF16、ZeRO-3 和梯度检查点，训练长度上限设为 8192；三阶段从上一阶段完整权重继续，验证集固定。”

**提升原因：**“全参路线允许模型整体适配乐园工具协议和长轨迹；阶段数据则先强调规范调用，再加入复杂规划与恢复过程。”

**失败案例：**“只确认 32B 权重能加载还不够，训练还要容纳梯度、优化器和长序列激活。当前 GPU 实验尚未执行，显存峰值需要首轮实测。”

**个人贡献：**“我把训练入口、数据转换和后续 GRPO 的模型路径统一到完整权重，避免前面说全参、后面仍加载旧 adapter。”

## D. SFT 加多轮 GRPO

**定义：**“SFT 学习教师怎么查乐园信息和规划，GRPO 根据学生自己走出来的八条同题轨迹计算相对优势。”

**基线：**“用 SFT 模型作为直接对照，重点看 GRPO 后有没有减少重复查询、改善恢复和最终行程合规。”

**实验设置：**“veRL 的 AgentLoop 把动作发送给工具服务，再把观察接回上下文；保留生成概率和动作掩码，固定 SFT 作为 KL 参考。”

**提升原因：**“学生会遇到自己前一步选错工具的状态，多轮 rollout 可以让修正后的任务结果反馈到训练，而不是只模仿教师第一步就选对的轨迹。”

**失败案例：**“八条轨迹都输出无法验证的行程时会全部归零，组内没有区分信号；需要从 rollout 找到是格式问题还是规划条件冲突。”

**个人贡献：**“我把整段工具交互接入训练，确保评分覆盖最终行程，并把环境观察从策略动作损失里排除。”

## E. 六维奖励

**定义：**“六维是格式、轨迹合理性、效率、行程约束、调用状态和答案质量，每条轨迹保存分解。”

**基线：**“针对最终交付，我用只相信中间规划成功的做法作为回归对照，检查最终答案被改写时是否仍会错误放行。”

**实验设置：**“答案权重从 0.60 逐步到 0.75，测试使用固定阶段；最终 itinerary 和最后成功规划结果比对后，再按原始游客偏好校验。”

**提升原因：**“模型不能通过修改时间表、删除指定烟花来换取表面可行，也不能用格式分补偿最终规划失败。”

**失败案例：**“亲子规划工具返回正常，最终答案把第一项改成凌晨零点，即使 Judge 给满分也会被门控拒绝。这是已有本地回归案例。”

**个人贡献：**“我补上最终答案证据核对，并让清洗和奖励共用这套检查，阻止同类错误同时进入数据和评分。”

## F. 边界样本降权

**定义：**“边界样本是最终通过检查，但出现过格式修复、部分工具失败或 Judge 边界评分的轨迹。”

**基线：**“对照方案是让这些样本与无瑕疵轨迹等量曝光，专项查看协议错误和工具恢复表现。”

**实验设置：**“LLaMA-Factory 数据预处理按阶段生成曝光次数；边界样本相对 pass 的比例从 0.30 增到 0.60，原始任务标识不变。”

**提升原因：**“初期让模型更多学习规范工具请求，后期再增加带修正过程的示范，兼顾协议学习和恢复行为。”

**失败案例：**“只在 JSON 里保存 weight，而训练器不读取它，仍然是等权。当前通过实体化曝光清单保证采样分布确实改变。”

**个人贡献：**“我把清洗质量标签连接到训练实际读取的数据，并校验标签与权重一致，避免标签只是记录字段。”

## G. 九个工具与调用成功率

**定义：**“九个是统一注册的工具数量；调用成功率按逻辑请求的 ok 结果统计，和整道题是否完成分开。”

**基线：**“各个模型使用同一个工具注册表和快照，不通过换接口来制造调用成功率差异。”

**实验设置：**“工具执行前验证 schema，失败也写进轨迹；一次请求内部网络重试不重复计数，模型修正后重新发请求则另计一次。”

**提升原因：**“明确错误让模型知道哪里需要修正，固定快照则让不同 checkpoint 面对相同的排队和演出信息。”

**失败案例：**“walk_time 的区域错误可以通过 HTTP 200 返回 ok:false，只看 HTTP 状态就会把失败算成成功。”

## H. 多模型交叉评测

**定义：**“至少两个独立 Judge 分别看同题的两条轨迹，每个 Judge 再交换 A、B 位置评一次。”

**基线：**“同一个 Judge 第一次的结论可以和交换后及另一个 Judge 的结论直接对照，看胜负是否稳定。”

**实验设置：**“输入模型评测必须有相同协议摘要和快照；配置排除学生及教师身份，每次保留理由，分歧标记 reviewRequired。”

**提升原因：**“可以定位某个模型是不是仅因答案位置或表达风格获胜，并把有争议的乐园题单独拿出来查证据。”

**失败案例：**“一条行程写得很详细但漏掉烟花，另一条简洁却保留全部约束。复核先查演出约束，再检查 Judge 是否被篇幅带偏。”
