## 第一部分：数字与技术选择的六段式答案

读法：定义说“测的是什么”；基线说“跟谁比”；实验设置说“怎样保证可比”；提升原因区分证据与推测；失败案例说“边界在哪里”；个人贡献说“你具体做了什么”。**没有做过对照实验，就直接说尚无对照，不补造基线。**

### 卡 1：306 条、1800+ 条、187 条、202 条、1500+ 条

**定义：** 种子是原始任务 query 及约束、类别等元数据；扩增任务是改写后的 query；轨迹是 query 在工具环境中完整运行的记录；清洗后训练样本又是第四种数量。四者不能混称。

**基线：** 306→1800+ 是老师原版数据叙述。迪士尼旧记录是已提交 187 条、目标约 300→1500+；本次实际数文件得到 202 条模板种子、12 类。

**实验设置：** 默认扩增 4 个变体，加原句，每种子最多按计划形成 5 条候选。202 条对应 1010 条计划候选，之后还会有生成失败和去重。应分别记录原始种子、扩增候选、去重保留、蒸馏成功、清洗保留、实际训练读入数量。云端历史训练文件未在此次核验范围内。

**提升原因：** 扩增预期改善表达覆盖，约束组合才决定任务覆盖；仅改写句子不会凭空增加独立任务难度。尚无消融证明“增加到某规模带来多少提升”。

**失败案例：** 同一个“110cm、下午入园”种子的多个改写随机分到训练和测试，会造成语义泄漏。必须按原始 seed_id／任务家族分组划分，再扩增。

**个人贡献：** 待确认你是否设计 persona×约束采样、去重与分组划分，以及是否亲自跑过扩增、蒸馏。不能将老师的 306 条归为自己的采集。

### 卡 2：真实语料 30%–50%、人工抽检 5%–10%、3-gram 阈值 0.8

**定义：** 30%–50% 和 5%–10% 是文档提出的目标比例；0.8 是代码里字符 3-gram 集合 Jaccard 去重阈值，交集大小除以并集大小，超过阈值判近重复。

**基线：** 当前种子文件 202/202 标记为 template，没有已兑现的人类语料比例。没有看到不同去重阈值的效果对照。

**实验设置：** 应记录来源、采集日期、脱敏过程和标注规则；人工审核按类别分层抽样。当前去重去空白后构建字符 3-gram，阈值比较为严格大于 0.8。

**提升原因：** 人类提问能补充口语、省略、歧义；去重能减少重复表述占用训练预算。这些是设计动机，不是已验证的百分点收益。

**失败案例：** 语义相同但措辞不同会漏去重；只有一个数字不同的任务可能被误去重，例如身高刚好跨过项目门槛。需要保护关键约束差异，不能只看文本相似度。

**个人贡献：** 待确认真实语料是否由你整理、抽检是否执行、有无审核表。只有入口代码时，讲“预留接入与审核机制”。

### 卡 3：9 个工具、数十次调用、平均 6.6 次

**定义：** 9 是注册表工具数量；数十次是执行器上限／设计能力，必须有成功轨迹才能讲成已验证编排能力；6.6 是旧教师基线记录的平均调用数。

**基线：** 原版的八类工具覆盖开放域出行。改造版改成排队、评论、规划、地点、演出、价格、步行、校验和天气。

**实验设置：** 长程能力要同时报告任务数、完成率、调用数分布和最长成功轨迹，并固定环境快照。不能用 max_turns 配置证明成功跑过那么多轮。

**提升原因：** 封闭工具集合缩小动作空间，统一 schema 减少协议歧义；沙箱降低外部故障噪声。但工具越多不必然越强。

**失败案例：** 反复调用同一个工具也能凑出 30 次交互；这可能是死循环。天气存在注册项也不代表实时天气已接通。

**个人贡献：** 待确认工具注册、服务化、执行循环分别由谁实现；用一段完整运行记录证明你的编排工作。

### 卡 4：交互成功率 99%+／100%（199/199）

**定义：** Notion 记录为沙箱交互 199/199。它至多支持对应样本中的技术交互成功；需查原始记录确认是否按 ok=true 统计。HTTP 200 不等于工具业务成功，更不等于最终任务完成。

**基线：** 没有核到同一批任务在 live 模式下的可比失败率，不能声称从某个线上低值提升到 100%。

**实验设置：** 固定数据快照、工具版本、调用参数、重试策略。至少分别报告首尝试成功率、允许重试后的逻辑调用成功率、整条任务完成率；所有失败都纳入相应分母。

**提升原因：** record & replay 消除了配额、网络和第三方波动，适合训练环境复现；这不证明线上供应商可靠性。

**失败案例：** 返回 ok=false 的错误信封仍然是 HTTP 200；若只统计状态码会虚高。全部用合成夹具也不能证明真实数据覆盖。

**个人贡献：** 待确认你实现的重试、超时、回放和计数逻辑；199 次原始日志尚需补齐。

**个人贡献：** 待确认是否只是完成清洗，还是打通了训练消费端；面试时把二者分开。

### 卡 11：单卡 A800 80G、32B、4-bit、LoRA r=16

**定义：** QLoRA 量化并冻结基座，训练低秩 adapter；代码为 NF4、double quantization、BF16 计算，r=16、alpha=32、dropout=0.05，覆盖注意力与 MLP 的七种投影层。

**基线：** 对比动机是全参数训练的显存需求；未核到同环境 full fine-tuning 或不同 rank 的质量／耗时消融。

**实验设置：** 32B 参数按四位粗算约 16GB 纯权重存储，但总显存还包括量化元数据、激活、adapter、梯度、优化器和生成缓存。代码注释“约60GB”不是本次测量值；不能仅由权重大小保证训练一定装得下。

**提升原因：** 降低可训练参数和基座权重内存，让单卡实验更可行；梯度检查点以重算换显存。

**失败案例：** 长序列或组采样增加生成与激活内存，仍可 OOM；4-bit 不表示全程用四位计算。没有尺寸消融，不能声称 32B 是已证明的最优甜点。

**个人贡献：** 待确认你做过显存排查、rank 选择、训练恢复或配置调整中的哪些事项。

### 卡 12：SFT 3 epoch、lr=1e-4、8192、batch=1×16、5% 验证

**定义：** 当前 SFT 脚本配置三轮、学习率 1e-4、每设备 batch 1、梯度累积 16；样本随机划出 5% 验证。8192 写在 dataset_kwargs 中，是否被实际安装版本正确消费需查运行日志和分词结果。

**基线：** 应比较同模型训练前与 SFT 后，并保持 prompt 和测试集一致；教师模型不是学生同基座的替代基线。

**实验设置：** 应按任务家族划分后再扩增，检查完整 prompt 长度、截断、EOS、chat template、assistant token 的监督掩码。审计文件明确：当前全量 transcript 的 assistant-only loss masking 尚未验证。

**提升原因：** SFT 学习协议与动作示范；但用户／工具返回若也进入预测损失，会改变学习目标，应核实而非默认“只训 assistant”。

**失败案例：** 同源改写随机泄漏到 5% 验证集；有效上下文长度参数未生效；监督了工具返回标签导致角色混淆。后两项应结合实际 labels／数据诊断，不能仅凭猜测定因。

**个人贡献：** 待确认你检查过哪些批次的 input_ids、labels、tokenizer 模板与 loss。

### 卡 13：GRPO 每题 6 条、beta=0.02、30 步、lr=2e-5

**定义：** 当前小试验配置 G=6，KL 系数 0.02，默认最大 30 步，学习率 2e-5；temperature=1.0、top_p=0.95、completion 上限 768，batch 6、累积 2。这些是当前脚本配置，不是旧奖励曲线的全部运行溯源。

**基线：** 从 SFT adapter 继续优化，与相同 SFT checkpoint 做成对评估。代码存在不代表新 30 步实验已经完成；审计说明没有新 GPU 训练结果。

**实验设置：** pin 训练库版本；核对参考策略究竟是固定 SFT，还是 PEFT／TRL 默认参考方式；不能仅凭 beta 就断言 KL 正在约束到 SFT。保存每题六个输出、reward、advantage 和 KL。

**提升原因：** 同题组内比较给出相对优势，无须单独训练 critic；代价是每题多次生成。G=6 是实验取值，不是有证明的最优组大小。

**失败案例：** 六条全得零或全满分，组内优势无有效区分；beta 太大限制学习，太小允许过度偏离；错误奖励会把错误行为强化。

**个人贡献：** 待确认你调整过哪些超参、观察过哪些曲线，以及实际跑的是旧版还是 v2。

### 卡 14：90 分钟、2／5 分钟容差、五项约束

**定义：** 当前 TS 校验器检查时间连续、身高、离园、套餐 LL 起始间隔、入园；常量为间隔 90 分钟、衔接／入园容差 2 分钟、离园容差 5 分钟。输入无效时另行失败。

**基线：** 相比仅由 LLM 给“可行性”分，程序能稳定复核已编码规则；这不意味着规则本身一定完整、正确或等同当前园区规定。

**实验设置：** 必须区分领域真实规则与模拟环境假设。此次只核对代码，未验证“90分钟”是上海迪士尼真实适用权益规则；面试将其称为当前模拟规则，后续需按乐园／产品版本配置并核实。

**提升原因：** 可执行检查能减少语言表达对评分的影响；真正价值取决于数据来源、规则覆盖和最终输出一致性。

**失败案例：** 当前该校验器没有烟花锚点完整性检查，也没有在时间衔接里加入步行耗时。项目 ID 查不到时身高约束还可能被跳过。不能说“六条硬约束全部验证、无法 hack”。

**个人贡献：** 待确认你定义和实现的检查项；能解释一个未覆盖边界和补测方案，比泛称“完全可验证”更可信。

### 卡 15：P@5=0.78、150 工具用例、100 场景、70 项断言

**定义：** P@5 是检索前五条相关比例的按 query 聚合指标；不是回答准确率。150／100 是文档中产品评测规模，70 是旧阶段测试断言数量，均不等于 RL 独立测试样本数。

**基线：** Notion 标注 P@5=0.78 为产品侧原有结果。本次未核对其标注集、分母、原始结果及对应提交，不能归为 RL 带来的提升。

**实验设置：** 补充检索 query 数、人工相关性定义、不足五条的计分规则、基线检索器与同一语料版本；断言数量随代码增长，引用时绑定提交。

**提升原因：** 只有相同标注集上的检索器对比才能解释 P@5 提升；自动化断言通过只验证覆盖到的功能，不证明模型效果。

**失败案例：** 检索结果与问题相关，但给出错误事实；100 个约束场景若被拿去构造训练种子，再用于最终测试，就不是独立测试集。

**个人贡献：** 待确认这些是你负责的产品模块、继承资产还是你补做的评估；没有原始证据时不写进主要效果句。

### 卡 16：15 分钟录制、零 API 成本、静态 POI 规模

**定义：** 15 分钟是快照采集计划间隔，不能当作数据绝对新鲜度保证。“零 API 成本”限于本地工具回放，不包括教师推理、GPU、在线 Judge、采集、存储。26 项目／12 餐厅／15 拍照点是改造文档某版本的静态覆盖说明，本次未对当前各园区列表逐项重数。

**基线：** 相比每次 rollout 都访问第三方，回放降低网络成本和波动；未核到总训练成本的量化对照。

**实验设置：** 同时固定快照时间、文件版本、时区和来源；记录采集失败与缺口；区分真实录制与合成 fixtures。新增乐园要验证数据和 ID 映射，而不只是加配置。

**提升原因：** 把采集与训练解耦，重复实验无需重新访问外部数据。

**失败案例：** 没有固定 snapshot_at 就默认取最新数据；历史请求选了未来数据；夹具兜底被当作真实观测；配置的采集调度实际延迟。

**个人贡献：** 待确认录制、回放、数据映射由你负责的部分。当前未核实的静态数量不要硬背。

### 卡 17：DeepSeek-V3 教师与蒸馏

**定义：** 教师生成任务改写或工具使用示范，学生学习这些示范；蒸馏不是把所有教师知识完整复制过来。

**基线：** 可选其他教师，或用强模型直接服务作为产品基线；当前未做多教师成本质量的严格对照。

**实验设置：** 记录真实 API model ID／版本、提示词、采样参数、工具环境与数据过滤。扩增脚本温度 0.9 不等于蒸馏所有阶段都应使用这个温度。

**提升原因：** 选型动机为中文、工具使用、调用成本和兼容性；教师在目标任务上的质量比学生好才是核心，不是“参数必须更大”。

**失败案例：** 教师选择工具正确却使用错协议；教师把观察结果写进 assistant 的 tool_response；改写遗漏身高但继承原 profile。复制 profile 不能保证 query 语义没变。

**个人贡献：** 待确认教师选型、prompt、批量运行和质量审核的归属。不要把 API 别名当作永久固定模型版本。

### 卡 18：SFT→GRPO，而非直接强模型 Prompt

**定义：** SFT 学示范中的动作和协议；GRPO 在当前策略生成的候选上利用相对奖励优化。工具环境本身无需可微。

**基线：** 强模型＋合理 prompt 必须是有效产品基线；同基座 base／SFT／SFT+GRPO 是训练消融基线，二者不可相互替代。

**实验设置：** 同任务、同工具、同上下文和预算比较任务完成率、约束通过、延迟、成本；现有历史数据不足以证明自训更便宜或超过强模型。

**提升原因：** 自训提供协议定制和领域奖励优化能力；SFT 初始化可能减少无效探索。不能说所有模型“不 SFT 就一定不能 RL”。

**失败案例：** 学到的仅是标签和首步工具选择，而不是多轮规划；或大多数题 SFT 已足够，RL 反而增加直接回答倾向。

**个人贡献：** 待确认你如何选择基线、设计奖励、运行实验和解释负结果；不能以“面试考训练”替代业务选型依据。

### 卡 19：文本协议、HTTP 环境、record & replay

**定义：** assistant 产生 think 后接 tool_call 或 answer；执行器产生 tool_response。工具注册、调用、奖励通过清晰接口分离；回放从快照读取观测。

**基线：** 与直接嵌在前端／单个供应商 SDK 的链路相比，统一协议便于数据、执行器、训练与评估对齐。开源模型并非不能学原生 function calling，自定义文本协议只是工程选择。

**实验设置：** 一个解析器与一份注册表是契约源，快照文件校验防漂移；严格区分模型生成与执行器结果；固定快照日期并检查多轮动作链。

**提升原因：** 减少各模块对格式理解不一致，便于重放和定位失败。

**失败案例：** 历史训练／评测把 tool_response 作为模型调用，而运行时只接受 tool_call。这个真实协议问题比泛泛说“上下文太长”更值得讲。

**个人贡献：** 待确认你定位、实现或验证了协议哪部分；若修复是后续协作成果，应照实说明。

### 卡 20：规则规划器＋偏好档位、评论 RAG

**定义：** 模型理解偏好并调用工具，规划器计算候选路线；评论检索补充主观体验。文档把它称为 TSP，但实际乐园任务还包含时间窗、项目选择和固定演出，不能直接等同标准“访问全部节点一次”的 TSP。

**基线：** 可与固定偏好档、随机路线、最近邻规则、纯 LLM 行程作对照；本次未核到完整路线质量消融。

**实验设置：** 固定候选项目、排队快照、步行成本和用户约束；验证 efficient／balanced／easy 的行为差异。数值成本相加前应统一量纲，权重档位的效果需要实际路线验证。

**提升原因：** 将可确定计算交给工具，模型负责语义偏好与决策；RAG 提供外部评论证据，减少纯常识回答。

**失败案例：** 规划器本身已完成主要优化，模型只选工具；若要声称 RL 学会权衡，需检查 profile 参数和最终路线。评论“适合亲子”不能覆盖官方身高限制。

**个人贡献：** 待确认路由器、规划器、评论检索哪些是原产品已有、哪些为你的改造；不要把接入已有优化器讲成独立研发求解算法。

### 卡 21：LLM-as-Judge／多模型交叉评分

**定义：** 主观答案用模型评分，客观事实与可编码约束优先由工具／规则验证。当前 Judge prompt 是匹配度、可行性、丰富度、清晰度四维；并非文档所称五维分别出分。

**基线：** 与单 Judge 相比，多 Judge 平均能降低个别模型偏差，但不保证独立或正确。当前实现支持取均值，未核到完整多模型交叉评测结果。

**实验设置：** 固定 rubric 和证据快照，隐藏模型身份，双顺序配对，控制冗长偏好，抽样人工校准；这些完整抗偏差措施尚不能说均已实现。

**提升原因：** 多视角有助于识别个别模型的偏好，但若都看不到事实证据，仍可能共同误判。

**失败案例：** 当前 LLMJudge 只接收问题、profile、答案，未把完整工具观测送进 prompt；“真实排队多少”无法被可靠核验。解析失败还返回中性 0.5，应独立记评测失败而不是悄悄当作有效分。

**个人贡献：** 待确认 rubric、评估模型选择、人工复核与冲突处理的实际工作；支持插件接口不等于已经完成交叉评测。

## 第二部分：27 题面试口述与追问

以下按你的问题顺序排列。“口述”可以练习；“追问”是面试官最可能继续挖的地方；“边界”提醒当前证据不足处。

### 1. 用 3 分钟介绍业务目标、技术方案和最终效果

**口述稿，约 3 分钟；个人负责范围请按实际替换：**

这个项目是一个面向乐园场景的行程规划 Agent，以迪士尼为第一个应用场景。用户可能同时提出孩子身高、入离园时间、必玩项目、少走路和观看演出等要求。目标是让系统根据园区数据生成有依据、能检查约束的行程，并在工具失败时给出合理反馈。

我是在通用出行规划方案基础上做领域改造。园区的优势是项目集合和部分规则比较明确，因此除了让大模型评价答案，还可以把身高、时间衔接、入离园等条件写成程序校验。但封闭场景不等于所有数据都可靠，实时数据、静态资料和沙箱合成数据需要明确区分。

系统分为工具环境、Agent 协议、数据、奖励和评估几层。工具环境注册了九个工具，覆盖排队、评论检索、行程规划、地点信息、演出、价格、步行、约束检查和天气。模型负责理解用户偏好、选择工具和组织答案，具体路线计算交给规划器。训练调试可以回放固定快照，减少真实 API 波动。

模型实验采用 Qwen2.5-32B-Instruct，单卡 A800 上用 QLoRA 做 SFT，并尝试从 SFT adapter 继续做 TRL GRPO。数据侧有结构化种子、表达扩增、教师蒸馏和清洗管线。当前仓库可核对到 202 条模板种子，真实语料比例和更大的轨迹规模仍要以训练数据文件为准。

效果方面，我会区分系统能力和模型证据。历史困难集 44 题上记录过较大的首步格式、工具选择差异，但后续审计发现旧协议和评测存在不一致，不能直接把它当作完整行程成功率。当前明确的改进方向是统一训练与运行时协议、去掉没有执行证据的奖励，并在固定 prompt 和独立测试集上重新做成对评估。

我最希望展开的是【你亲自负责的模块】：例如如何将自然语言偏好映射到规划参数、如何保证工具调用与观察消息不混淆、以及怎样让奖励真正对应可验证的行为。这个项目让我认识到，训练分数上涨只是开始，协议一致性、奖励可信度和独立评测决定结果是否能用于产品。

**追问：** “所以现在效果到底怎么样？”答：有完整系统模块和历史训练探索；当前证据未充分证明端到端成功率提升。不要用模糊的“大幅提升”绕开。

### 2. 为什么端到端训练，而不是强模型加 Prompt？

**口述：** 强模型＋工具＋合理 Prompt 是可行且应比较的基线。训练的动机是把协议、工具选择和领域约束固化到可部署模型里，并允许在领域奖励上继续优化。是否值得训练取决于同等质量下的成本、延迟、部署要求与维护成本，不能先假设自训必胜。

**深挖：** 真正多轮端到端 Agent RL 应当由学生生成动作、执行器执行、回传观测、继续生成，最后把任务回报用于更新。当前 TRL 首步实验没有这条多轮环境交互链，因此应称“面向 Agent 的首步策略后训练”，不能把名字当成已完成实现。

### 3. 306 条任务种子怎么来，如何扩成 1800 多条轨迹？

**口述：** 先纠正项目版本：306→1800+ 来自老师原版，且原文是先扩写任务再蒸馏轨迹。我改造版当前有 202 条模板种子，按 persona、约束与十二类任务生成。默认每条做四种表达改写，加上原句，再用 3-gram Jaccard 去重。之后教师运行工具循环，才能生成轨迹；清洗后才是 SFT 样本。

**追问：** “202 条怎么扩到 1800？”答：默认配置不能。除非增加种子、变体或重复 rollout，并提供实际文件与日志。不能把不同阶段的目标数拼起来。

**更深一层：** 种子生成器中部分 query 的明确限制和 profile 未必完全同步，例如“某项目必玩”只写进 query。要测试 query→profile 的一致性，不能让奖励按未表达或遗漏的 profile 判模型对错。

### 4. 训练轨迹包含哪些字段，如何表示四种内容？

**口述：** 轨迹至少包含任务 ID、类别、园区、用户 query、教师、消息序列、结束原因、答案、调用数、格式错误数、是否补救，以及每次调用与执行结果。当前清洗输入类型还有 source 和 difficultyHint；未来审计应补模型精确版本、快照 ID、采样配置及耗时。

**协议示例，内容用于说明，不是实验日志：**

```text
system：固定园区、日期、工具 schema、协议
user：帮我查一下创极速光轮的排队时间
assistant：<think>先查询排队数据。</think><tool_call>{"name":"get_wait_times","arguments":{"park_id":"shanghai","ride_id":"tron"}}</tool_call>
user（执行器注入）：<tool_response>{"ok":true,"result":{"waitMinutes":75}}</tool_response>
assistant：<think>依据返回结果回答。</think><answer>当前这份工具数据中等待时间约75分钟。</answer>
```

**必须会解释：** 这里 think 是训练协议中的文本字段，不等于可观测到模型全部内部推理。工具返回由执行器写入；当前自定义协议以 user role 承载 tool_response，不是 assistant 伪造，也不是原生 tool role。assistant 每步只能 tool_call 或 answer 二选一。

**追问 loss：** 设计上应只对 assistant 生成位置训练；实际 SFT 脚本的 mask 未验证，不能回答“已经全部正确遮掉”。

### 5. DeepSeek-V3 教师如何控制质量与多样性？

**口述：** 把任务多样性和答案质量分开管。任务侧靠 persona、约束、类别和不同表达风格；质量侧靠教师真实调用工具、协议校验、结束条件和清洗。扩增当前温度是 0.9，适合增加表达变化，但不能仅靠升温制造任务多样性。

**细节：** profile 原样复制不能防止改写遗漏约束，需要抽取 query 中人数、时间、身高、否定条件进行一致性比对。相同 seed 的变体应该一起进入同一数据分区。恢复成功的失败轨迹值得保留，但错误事实、伪造工具结果不能当作多样性。

**边界：** 教师选择只证明采用了哪个来源，不证明所有示范高质量；原文“教师必须显著更大，否则无信息增益”过于绝对。

### 6. 多阶段质量过滤分几层，各淘汰什么？

**按当前代码回答：**

1. 消息归属：剔除 assistant 伪造 tool_response。
2. 规则健康：模型错误、超时、无答案、达到最大轮数、答案少于 8 字符、中文字符不足 2、格式错误覆盖每步等。
3. 工具健康：有调用但所有调用均失败的轨迹丢弃；部分失败但后续恢复不必全删。
4. 协议清洗：剥离标签外文本后，再严格解析所有 assistant 消息；仍不合法则丢弃。
5. 分级和权重：≤3 次 easy，4–10 次 medium，>10 次 hard；完美 1.0，其余 borderline 0.6。
6. 可选 Judge 门：低于 0.35 丢弃；0.35 到不足 0.6 降权。

**口述收尾：** 文档叫三级漏斗，实现可以拆成上述步骤；数字不必强凑。当前 clean.ts 没有直接调用硬约束校验器，不能说每条 SFT 行程都已经过规则验证；无工具的常识任务也不是一律丢弃。

### 7. 为什么按工具次数分级，它能代表难度吗？

**口述：** 它是成本低的代理指标，反映交互长度和上下文压力，但不是任务本质难度。重试和冗余能把简单题变长；一次 plan_itinerary 调用也可能封装复杂优化。

**更合理的设计：** 结合硬约束数量、依赖深度、工具种类、动态信息、冲突恢复与路径选择空间。难度标签应尽可能来自任务本身，不能完全由教师低效行为决定。

**边界：** 原版 ≥14 留了 11–13 空档，改造文案 ≥10 与 medium 4–10 重叠。当前代码是 ≤3、4–10、>10。排序文件不等于课程训练已生效。

### 8. 边界样本动态降权如何实现，权重怎样定？

**口述：** 当前准确实现是静态分档：清洗记录 1.0 或 0.6，可选 Judge 再调整；还没有证据证明训练消费了这个权重。转换为 conversations 时 weight 被丢弃，所以不应称已实现动态降权。

**如果问应该怎样落地：** 可用逐样本平均 token loss 后加权：L=Σw_iL_i/Σw_i；或按权重调整采样概率，先明确二者不同。不建议对 advantage 随意乘权重然后声称等价于 SFT 样本加权。

**验证：** 构造两条可区分样本，检查有效采样频率或梯度贡献；对比不加权、删除边界样本、0.6 加权。0.6 是启发式选择，不是实验已证明最优。

### 9. SFT 后为什么还需要 GRPO？仅 SFT 有什么问题？

**口述：** SFT 模仿教师轨迹，偏向“在教师已经走对的历史里预测下一步”。推理时模型会遇到自己造成的错误状态，SFT 不一定覆盖。GRPO 可以比较当前策略产生的候选，把更符合任务目标的行为提高概率。

**项目例子：** 教师示范直接查询成功，学生却先传错 ID；如果训练始终没有错误反馈，学生可能不会恢复。真正改善这种问题，需要多轮 rollout 真执行工具，不能只奖励首个工具名。

**边界：** 当前旧困难集提供了协议不稳的线索，但受历史评测问题影响，不能独立证明 GRPO 改善了长程规划。简单题 SFT 可能已足够，RL 需要报告回退。

### 10. GRPO 目标函数是什么，与 PPO 有什么区别？

同一问题采样 G 个输出，以组内奖励作基线：

\[
\hat A_i=\frac{R_i-\operatorname{mean}(R_1,\dots,R_G)}{\operatorname{std}(R_1,\dots,R_G)+\epsilon}.
\]

一个常见的原始 GRPO 表达为：

\[
J(\theta)=\mathbb E\left[\frac1G\sum_i\frac1{|o_i|}\sum_t
\left(\min(\rho_{i,t}\hat A_i,\operatorname{clip}(\rho_{i,t},1-\varepsilon,1+\varepsilon)\hat A_i)
-\beta D_{KL}(\pi_\theta\Vert\pi_{ref})\right)\right],
\quad \rho_{i,t}=\frac{\pi_\theta(o_{i,t}\mid h_{i,t})}{\pi_{old}(o_{i,t}\mid h_{i,t})}.
\]

**口述：** 奖励高于同题平均的候选被强化，低于平均的被抑制；clip 限制相对旧采样策略的更新，KL 约束相对参考策略的偏离。常见 PPO 用 critic 估计价值和优势；GRPO 用组内相对奖励，省去 critic，但增加多候选生成成本。old 和 ref 不是一个概念。

**工程追问：** 全组同分时优势没有区分度；多轮训练只应更新模型生成 token，工具观测不是模型动作。不同 TRL 版本支持不同归一化、loss 类型和 KL 默认值，以上公式不能替代实际安装版本配置审计。[GRPO 原论文](https://arxiv.org/abs/2402.03300)；[TRL 官方说明](https://huggingface.co/docs/trl/grpo_trainer)。

### 11. 六维奖励是什么，每维如何计算？

**这里说的是多轮 TS 实现，不是当前 TRL 首步 v2：**

| 维度 | 当前实现 |
|---|---|
| format | 1−格式错误数/步骤数；答案补救再扣0.2；无答案扣0.3，截到[0,1] |
| trajectory | 按类别匹配期望工具；部分类型命中任一允许工具即满分；trade_off／多意图无调用0、仅一种0.4、至少两种1；no_tool 对不必要调用扣分 |
| efficiency | 1−0.2×完全重复调用数−0.1×超出难度上限次数；上限easy4、medium12、hard20，截到[0,1] |
| constraints | 仅 plan_request 提取最后一次成功规划结果，重跑校验，得通过检查数/检查总数；找不到行程为0；其他类别为1 |
| callStatus | 每个失败调用扣0.25；后续同名工具成功则该次只扣0.1，截到[0,1] |
| answer | 可插拔 Judge；启发式或 LLM 0–10 归一化为[0,1] |

**更深的追问：** 当前 constraint 奖励检验最后成功的工具行程，未保证最终自然语言答案忠实于该行程；且规划请求以外的权衡／多意图不检查行程约束。不能说它全面验证了最终答案。

**当前首步 v2：** 非法协议／未知工具／schema 错误为0；合法但工具错0.1；正确工具0.5，加最多0.5的参考参数匹配；no_tool 非空答案仅0.2格式信用。它明确不评价真实执行和答案语义。

### 12. 六种奖励如何组合，怎样避免某一项支配？

**口述：** 用加权和，三阶段权重每行和为1，各维有界。但不能保证“不出现支配”：真正影响梯度的是各项在组内的差异、权重和相关性，恒定满分项即使权重大也不给排序信息。

| 阶段 | 格式 | 轨迹 | 效率 | 约束 | 状态 | 答案 |
|---|---:|---:|---:|---:|---:|---:|
| early | .15 | .12 | .08 | .12 | .08 | .45 |
| mid | .08 | .08 | .06 | .12 | .06 | .60 |
| late | .05 | .06 | .05 | .12 | .04 | .68 |

**需要监控：** 逐维均值／方差、饱和比例、与任务通过率的相关性、去掉某项后的结果。重要约束如果真不可违反，应考虑任务可行性门控或约束优化；当前代码只是加权和，不是硬否决。

### 13. 0.29→0.96 具体代表什么，测试集一致吗？

**口述：** 它是旧训练日志中早后期采样批次的代理分数，不是两个固定测试集分数，因此不能回答“同一测试集提升到96%”。日志真实第一条是0.330，后期有0.963，中间波动很大。更重要的是旧奖励中若干维度没有执行证据，后续已经重写为明确的首步评分。

**正确验证方式：** 冻结独立任务、prompt、解码、快照、奖励版本和 checkpoint，重跑每个阶段；把训练 reward 与测试集首步正确率、工具执行率、最终约束满足率画成不同指标。

**能背的结尾：** “我现在把它作为旧代理目标被优化的记录，不把它作为业务成功的证据。”

### 14. 观察到哪些奖励投机，有真实 badcase 吗？

**可核对的真实机制问题：** 旧单步训练奖励给了未执行工具的状态信用，并存在用工具调用获得答案信用的问题。历史日志 callStatus 始终为1；审计文档明确记录这些无依据分数已移除。

**可核对的类别级 badcase：** 历史 GRPO 的规划类10题全格式通过，工具正确却0/10。说明“格式漂亮”和“知道怎样完成规划”没有等价关系。

**必须讲清：** 当前没有这十题的逐题原始输出，所以不能编一个“某游客身高110cm、模型推荐某项目”的真实故事。可以拿此类问题做合成测试，但必须标“构造案例”。奖励函数有漏洞，也不自动证明某条策略主动利用了漏洞；需要输出轨迹才能证实行为。

**可补测试：** 无关工具凑两种、最终答案篡改工具行程、伪造 tool_response、隐藏项目 ID 绕过身高检查。它们是明确测试方向，不是声称已经观测到的四条真实日志。

### 15. KL 如何缓解奖励投机，系数过大怎样？

**口述：** KL 抑制策略相对参考分布变化过快，间接限制极端刷分行为，但不判断奖励真伪，也修不了错误奖励。beta过大时策略难以离开参考模型，reward梯度被抵消，可能学不动；过小时容易过度偏离，但是否有问题需看实际策略与验证指标。

**项目细节：** 脚本设置beta=0.02，不代表已经实现“发现偏离便自动增大KL”的动态控制。还要核对PEFT模式下参考策略到底是哪套权重；没有固定SFT参考快照就不能声称必定约束到SFT。

### 16. 课程式权重如何调整，何时切阶段？

**口述：** 多轮奖励提供early／mid／late三套表，答案权重45%→60%→68%。这是可选择的阶段配置；当前没有核到自动按验证集切阶段的机制，也不能把旧训练曲线当作已经完成三阶段调度。

**如果要求你设计：** 先明确阶段目标，前期减少协议无效输出，中期改善工具动作，后期提高任务结果。用开发集上持续稳定的格式率、有效执行率和无严重约束回退来决定切换；设连续窗口、防来回切换，并记录阶段事件。具体阈值应实验确定，不临时编“第100步／95%必切”。

**容易漏：** 训练阶段权重变化会改变reward定义；模型横向比较用固定评分表，否则升分可能只是换了尺子。

### 17. 九个工具怎么选，描述怎样设计？

**口述：** system prompt从工具注册表生成，包含名字、用途、输入schema。模型从用户意图输出单个tool_call，运行时再验schema和执行。描述要告诉模型“什么时候用、能返回什么、不能解决什么”，参数明确ID、单位、必填项与枚举。

| 意图 | 工具 | 关键参数／边界 |
|---|---|---|
| 当前排队／停运 | get_wait_times | park_id必填；ride_id可选 |
| 主观体验／值不值 | search_reviews | park_id、target_id、target_type、query；top_k默认3、范围1–20 |
| 生成行程 | plan_itinerary | park_id；profile、route_profile、start_area、avoid_rides等可选 |
| 地点事实 | get_spot_info | park_id、spot_id、spot_type；不能把名字当ID |
| 演出场次 | get_show_schedule | park_id；当前快照或默认 |
| 套餐信息 | get_ll_pricing | 无必填参数；当前静态价格库 |
| 区域步行 | walk_time | park_id、from_area、to_area |
| 草案校验 | check_constraints | park_id、itinerary；应传同一profile |
| 天气 | get_weather | park_id、可选date；live尚未实现 |

**追问：** 参数schema正确也不代表ID存在、数据新鲜或任务完成，要继续执行并检查观测。

### 18. 工具功能重叠时如何选？

**口述：** 看所需证据的范围和权威性。只问两个区域走多久就walk_time；询问一天怎么排用plan_itinerary；问项目身高要求用get_spot_info；问刺激感或体验用search_reviews。评论不能覆盖身高等硬事实。

**训练与评测：** 接受多条合理路径，标签可为允许工具集合；但不要只因类别广泛就接受所有工具。多意图任务中首步合理只是第一步，还要检查后续子需求有没有覆盖。

**已有漏洞：** trajectory对部分类别仅命中任一工具即满分，trade_off只计工具种类；这些不能充分判断“合理重叠选择”。

### 19. 参数错误、超时、空结果、冲突如何处理？

**口述：** 按错误类型处理，避免统一重试。

| 情况 | 做法 | 当前边界 |
|---|---|---|
| JSON／schema错误 | 拒绝执行，返回可定位的错误，让模型修参 | 严格协议与schema校验已有 |
| 参数结构对、ID不存在 | 返回业务错误，查询正确ID或询问用户 | 需执行层验证 |
| 临时网络失败／超时 | 有预算重试，超预算失败反馈，必要时切备用源 | live排队有重试、15s级上游超时；HTTP工具请求与episode还有外层限制 |
| 空结果 | 区分不存在、无数据、未知；不得把null当0分钟 | 排队会返回null／unknown或无数据错误；应逐工具检查 |
| 数据冲突 | 对齐园区、项目、时间和来源，优先权威且新鲜的证据，保留不确定性 | 主源失败切备用源不是完整冲突融合机制 |

**关键细节：** 工具业务失败用HTTP200＋ok=false信封；请求外壳格式坏可返回400，服务传输失败另算。重试参数错误没有意义。无限等待要有单次与episode两层时间预算。

### 20. 99%以上成功率的分母是什么？

**口述：** 我会报告“固定沙箱用例中逻辑工具调用的成功数／发起总数”，并说明重试是否合并。现有文档的199/199不是最终任务成功率；没有原始计数日志前，我不会把它扩展为线上99%SLA。

**必须区分：** 协议合法→参数合法→执行成功→结果可用→最终任务完成。这五层每一层的分母和失败条件不同。错误信封正常传回只能说明通信链路健康。

### 21. Key轮询如何设计，限流与并发安全怎么处理？

**口述：** 老师原版强调Key轮询；我这版训练环境主要用本地回放，本次未核到完整Key池实现。因此我能说明设计，但不把它说成自己的已上线模块。

**设计细节：** 对合法授权的key维护健康状态、可用额度、冷却时间、在途数；调度时原子预占配额。收到429按Retry-After退避并加抖动；认证失败暂停该key；网络错误有界重试。单进程可用受保护的共享状态，多进程需共享计数和原子租约，结束后释放。

**追问：** 同一账户多key可能共享额度，应同时控制账户／供应商级限流，不能把换key理解为绕过限制。推理key与数据源key要分开管理，不把key写进轨迹与错误正文。

### 22. 上下文压缩保留什么、丢弃什么，怎样验证？

**口述：** 优先保留原始用户硬约束、当前时间与位置、已完成项目、未满足需求、最近有效观测及其来源时间、尚未恢复的错误。可以移走重复工具返回、已失效状态和无关评论；不要直接截掉最早的用户条件。

**本项目当前边界：** 已有token／轮数预算与提前总结思路、评论top-k限制；尚未核到经过质量对照的完整结构化记忆压缩方案。Early-stop是终止策略，不等同信息无损压缩。

**验证设计：** 同一轨迹压缩前后比较关键字段保留、下一步动作、最终约束通过率；构造早期身高限制、否定要求和最新状态覆盖旧值的测试。保留原始trace以便追溯；自然语言摘要不能保证无损。

### 23. 长程前序错误积累，怎样检测纠正？

**口述：** 我把错误拦截放在三个位置：动作前校验协议和schema；执行后检查ok、数据来源和状态；最终交付前校验结构化行程。失败作为观察回传，让模型修参数、换工具或承认缺少数据。

**实现上的不足：** 当前callStatus用“后续同名工具成功”判恢复，这不一定是同一错误已经修好；更严谨要绑定逻辑调用ID、参数和目标。当前最终答案与工具规划结果的一致性也需要单独验证。

**追问：** 避免修错循环的方法是有限重试、重复动作检测、保留失败原因以及时间预算。没有可行解时解释冲突条件，不生成看起来完整的虚假路线。

### 24. 交通或天气发生变化，怎样重新规划？

**口述：** 对乐园场景，核心变化是排队、项目停运、步行可达性和演出状态。重规划从“当前状态”开始，锁定已完成事项，保留不可移动的锚点和用户硬约束，失效的旧观测重新查询，只优化剩余行程。

**设计细节：** 时间／位置／完成列表作为结构化状态；触发条件包括停运、锚点不可达和影响明显的等待变化；轻微波动用阈值或冷却避免不停改计划。生成候选后比较约束可行性与更改代价，再向用户解释变更。

**边界：** 当前实时天气未实现，不能说系统已根据真实天气自动重规划；该题是可落实的扩展设计。需要用不同时间快照、停运注入和状态一致性测试验证。

### 25. LLM-as-Judge哪些维度，怎样减少三种偏差？

**口述：** 当前prompt列匹配度、可行性、丰富度、清晰度，输出0–10总分及原因；规则能检查的部分单独计算。它目前未分别输出四维分，也未传完整工具证据，因此事实核验能力有限。

**位置偏差：** 做A/B配对时随机顺序并交换再判；前后不一致记为不稳定。当前单答案打分没有A/B位置，但未来配对时需实现。

**长度偏差：** rubric明确奖励有效信息而不是字数；用相同正确答案的简洁版／冗长版做校准，避免仅因长而高分。现有启发式还用了长度和数字特征，需防刷格式。

**自增强偏差：** 最终评测模型尽量不参与蒸馏或训练奖励；隐藏候选身份，加入人工复核。不同模型也可能共享偏差，不能说“换模型就消除了偏差”。

### 26. 为什么多模型交叉评测，Judge冲突怎么办？

**口述：** 多模型是为了暴露单模型风格偏好和不稳定性；当前EnsembleJudge实现的是简单均值，没有自动冲突裁决。也没有证据证明完整多模型终评已跑完。

**冲突处理设计：** 先看争议是不是可核验事实，交给工具数据／规则；主观偏好保留每位Judge分数和理由，对高分歧样本盲审或交第三方复核；无法裁决则报告不确定性。先校准各Judge量尺，再讨论均值或胜率。

**失败时：** 解析失败、网络失败不应默默当作有效中性分参与均值；当前LLMJudge解析失败返回0.5，是需要改进的点。

### 27. 迁移成企业经营分析Agent，哪些能复用？

**口述：** 可以复用协议、工具注册、执行器、失败反馈、轨迹记录、训练数据管线框架和分层评测思想。需要重建企业数据语义、权限、工具契约与奖励；学生模型是否可迁移要重新评估，不能只换prompt。

| 乐园模块 | 企业分析对应物 | 必须调整 |
|---|---|---|
| 排队／POI查询 | 指标库、数据仓库查询 | 时间粒度、组织维度、权限、SQL安全 |
| 评论RAG | 经营报告、指标口径、业务知识检索 | 来源、版本、访问范围 |
| 行程规划器 | 分析步骤与计算工具 | 先定义指标，后查询，再计算、解释 |
| 身高／时间规则 | 财务勾稽、公式、单位、时间范围校验 | 防重复join、币种混用、分母错位 |
| 回放快照 | 脱敏数据快照／冻结报表版本 | 数据隔离、可追溯、避免未来信息泄漏 |
| route_profile偏好 | 分析目标和权衡 | 利润、收入、库存等目标必须明确定义 |
| 多维奖励 | 查询合法、计算正确、引用可靠、结论支持度 | 规则检查不应被漂亮报告抵消 |

**例子：** “华东区利润率为什么下滑？”先确认本期／对比期、毛利率还是净利率，再查询可比口径数据，拆解收入、价格、成本或结构变化，最后给出有来源的结论。相关性不能自动称为因果；数据不足时输出缺口。个人贡献仍是定义和验证这个分析闭环，不能只包装九个新工具名。

## 第三部分：用一个例子真正串起全链路

练习问题：“带身高110cm的孩子，15点入园，20点离园，少走路，还想看夜间演出。”以下是**教学构造场景，不是实际园区数据或历史成功轨迹**。

1. **意图与约束：** 身高110cm、入园15点、离园20点是显式条件；少走路是偏好；演出是希望完成的目标。不能自行把离园时间改到21点。
2. **证据查询：** 查演出场次、候选项目身高要求、排队与步行信息。假设快照显示所需演出20:30才开始，则已发现与离园冲突。
3. **冲突处理：** 说明20点离园无法看20:30演出，询问是否延后或改看其他场次；不能用“尽量安排”掩盖不可行。
4. **规划参数：** plan_itinerary的profile传入孩子与时间，route_profile选easy。传错ID时反馈错误并修正，不能自己生成tool_response假装成功。
5. **结果校验：** 检查每项身高、前后时间与移动耗时、入离园、演出锚点。当前代码校验覆盖不全，演出与步行需额外补验。
6. **答案忠实：** 用户看到的时间表应与通过校验的结构化行程一致，不能在润色时把项目、时间改掉。
7. **轨迹进入训练：** 保存query、profile、模型版本、快照、assistant动作、执行器观测、结束原因；质量筛选；同源seed不跨训练测试。
8. **首步与全程区别：** 首步正确选择get_show_schedule只能证明第一步合理。跑完上述整个闭环并满足约束才是任务完成。

## 第四部分：面试前最值得练的追问

先不用背27题全文。按以下顺序，每题脱稿说60–90秒，再拿材料校对。

1. 你训练的模型是什么？它究竟是多轮Agent RL还是首步策略训练？
2. 202、306、1800+分别属于哪个版本、哪个数据阶段？
3. tool_call和tool_response分别由谁产生？标签错会有什么后果？
4. 95.5%和61.4%的分子分母是什么？为什么不能叫任务成功率？
5. 你的六维奖励在哪个文件实际执行？当前TRL用的是哪套？
6. 为什么有weight=0.6不代表梯度真的降权？
7. 规划题10/10格式对、0/10工具对，你会如何定位？
8. 一次工具技术成功如何逐层转化为最终用户成功？
9. 给出一条真实失败证据，以及你亲自做的诊断／修复。
10. 哪些事是老师方案、已有产品、协作产物、你自己做的？

个人贡献可填成一行事实：**“我负责____；最关键决策是____；我实现／修改了____；用____验证；留下的未解决问题是____。”** 不要泛称“整个pipeline都是我做的”，除非你能逐模块举证。
